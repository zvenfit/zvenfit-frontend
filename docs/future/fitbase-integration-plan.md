# План интеграций ZvenFit с FitBase

Статус: будущая инициатива; discovery и реализация не согласованы.

Этот документ не описывает текущую production-архитектуру и не является
активным обязательством по реализации или срокам.

Дата фиксации: 2026-08-13.

Версия для согласования с менеджером: [`fitbase-integration-manager-plan.md`](fitbase-integration-manager-plan.md).

## Цель и продуктовый принцип

Сайт помогает человеку выбрать клуб, направление, тренера и подходящее время. Запись на занятие остаётся в мобильном приложении ZvenFit: сайт не должен становиться альтернативным каналом web-записи.

Отсюда следуют решения:

| Сценарий | Решение |
| --- | --- |
| Кнопка «Записаться» на сайте | Не добавляем. Используем формулировку «Запись в приложении» и существующие ссылки App Store / RuStore / APK. |
| Web-виджет FitBase | Не встраиваем: он разрешает web-запись и конкурирует с целью установки приложения. |
| Прямая ссылка FitBase на занятие | В текущей документации это ссылка на карточку в web-виджете, а не подтверждённый deep link в приложение. Не используем. |
| Native deep link на занятие | Проверяем у FitBase. Если официально поддерживается, рассматриваем кнопку «Открыть в приложении» с fallback на магазины. |
| Расписание на контентных страницах | Показываем ближайшие занятия по услуге или тренеру; запись — только в приложении. |
| Свободные места и лист ожидания | Показываем обезличенный статус. Вступление в лист ожидания — в приложении. |
| Заявки с сайта | Надёжно синхронизируем в воронку FitBase, сохраняя текущие YDB и Telegram. |

Официальные материалы FitBase:

- [API v2 и доступные сущности](https://help.fitbase.io/article/21001)
- [Прямая ссылка на занятие в web-виджете](https://help.fitbase.io/article/28827)
- [Свободные места и лист ожидания](https://help.fitbase.io/article/3817)

| P1 | Заявки сайта → FitBase Lead | Единая воронка, меньше ручной работы, сквозная атрибуция | M–L | Поля Lead, справочники и политика дублей |

| P1 | Ближайшие занятия на страницах услуг | Связывает продающий контент с живым расписанием | M | Стабильный ID шаблона занятия или согласованный mapping |

Рабочая оценка до P0:

| Работа | Оценка, человеко-дни | Условие |
| --- | ---: | --- |
| API discovery | 0,5–1,5 | Есть Swagger, токен и доступ к настройкам FitBase |
| Надёжный MVP заявок → FitBase Lead | 4–7 | Без сложной маршрутизации и автоматического Task |
| Task и маршрутизация по филиалам | +1–3 | После стабильного MVP Lead |
| Пилот ближайших занятий | 2–4 | Одна страница услуги и одна страница тренера |

| Свободные места из готовых агрегатов Schedule | 1,5–3 | FitBase уже отдаёт корректные агрегаты |
| Свободные места через агрегацию ScheduleRegistration | 3–6 | Нужна пакетная загрузка, статусы и отдельный cache contract |
| Native deep link | 0,5–1 | FitBase официально поддерживает ссылку на нужное занятие |

Это диапазоны разработки, тестов и документации без ожидания ответов поддержки и без юридического согласования. Оценку уточняем после P0.

## P0. API discovery

Перед реализацией выполнить read-only spike на production-подобных данных, не выводя персональные данные в логи или публичный ответ.

Нужно подтвердить:

1. Возвращает ли `Schedule` стабильные идентификаторы тренера и шаблона занятия. Сейчас публичный proxy сохраняет только имя тренера и название тренировки, чего недостаточно для надёжного связывания страниц.
2. Есть ли в `Schedule` готовые поля количества записанных и ожидающих. Если нет — можно ли получить регистрации одним запросом за диапазон дат, без отдельного запроса на каждое занятие.
3. Какие статусы `ScheduleRegistration` считаются занятым местом, листом ожидания, отменённой или неподтверждённой записью.
4. Как FitBase предлагает скрывать количество свободных мест и должно ли это правило применяться к нашему API.
5. Поддерживает ли клиентское приложение ZvenFit universal link, app link или custom URL scheme на конкретное занятие.
6. Для `Lead`: обязательные поля, фильтры поиска, источник, UTM, филиал, этап воронки, ответственный, внешний ID и поведение при повторном телефоне.
7. Может ли отдельный токен иметь минимальные права: чтение расписания/регистраций и создание заявок только для нужных филиалов.
8. Покрывает ли текущая политика конфиденциальности передачу данных заявки в FitBase и нужно ли отразить FitBase как обработчика до запуска синхронизации.

Результат P0:

- зафиксированный transport contract и обезличенные fixtures;
- таблица идентификаторов тренеров, занятий, клубов, рекламного источника и этапа воронки;
- решение по дедупликации лидов;
- ответ FitBase по native deep links;
- уточнённые оценки P1–P3.

## P1. Ближайшие занятия на страницах

### Пользовательский сценарий

На странице услуги показываем 3–5 ближайших подходящих занятий. На странице тренера — его ближайшие групповые занятия. Карточка содержит:

- день, дату и время;
- название занятия;
- тренера — на страницах услуг;
- клуб и зал;
- обезличенный статус мест, когда он доступен;
- подпись «Запись в приложении»;
- единый блок ссылок App Store / RuStore / APK под списком.

Не добавляем web-запись и не используем CTA, который обещает запись прямо на сайте.

### Технический подход

1. Расширить публичный contract `fitbase-schedule` стабильными `trainerId` и `trainingId`, если P0 подтвердит поля.
2. Завести явный конфиг соответствий:
   - URL страницы тренера → `trainerId`;
   - URL страницы услуги → один или несколько `trainingId`;
   - при необходимости — ограничения по филиалу.
3. Сделать один переиспользуемый runtime-компонент, например `public/js/schedule-teasers.js`, вместо отдельной логики в каждой HTML-странице.
4. Подключать блок через `data-*`-атрибут или build marker. Не копировать разметку и скрипт по страницам вручную.
5. Использовать существующий `SCHEDULE_API_URL` и серверный proxy; токен FitBase никогда не попадает в браузер.
6. Добавить состояния загрузки, пустого результата и временной недоступности. Сбой блока не должен мешать чтению основной страницы.

### Критерии готовности

- на странице не показывается занятие другого тренера или направления;
- отменённые занятия не выглядят доступными;
- блок работает на 375 px и с клавиатуры;
- ссылки на приложение берутся из `scripts/app-links.config.json`;
- измеряются показ блока и клики по каждой платформе приложения с контекстом страницы;
- HTML/CSS/JS проходят `npm run build`, `npm run lint:public` и `npm run test:build`.

## P2. Свободные места и лист ожидания

### Что показываем

Рекомендуем не перегружать карточки точными числами во всех состояниях:

| Условие | Текст на сайте |
| --- | --- |
| Предварительная запись не нужна | Без бейджа мест |
| Запись открыта, мест достаточно | «Есть места» |
| Осталось мало мест | «Осталось N мест» |
| Группа заполнена, лист ожидания доступен | «Мест нет · лист ожидания в приложении» |
| Запись остановлена | «Запись закрыта» |
| Занятие отменено | «Отменено» |

Порог «мало мест» определить продуктово после просмотра реальных размеров групп; стартовая гипотеза — 3 места.

### Ограничения безопасности и актуальности

- Публичный API возвращает только агрегаты и статусы; имена, телефоны, `clientId` и сами регистрации наружу не выдаются.
- Сначала проверяем, есть ли агрегаты в `Schedule`. Если их нет, получаем регистрации пакетно и агрегируем в Cloud Function; не делаем N+1-запрос на каждую карточку.
- Текущий schedule response кешируется на 5 минут. Для мест это может быть слишком долго: после P0 выбрать отдельный короткий TTL или отдельный availability endpoint с учётом лимитов FitBase.
- Если данные о местах устарели или недоступны, скрываем бейдж мест, но продолжаем показывать само расписание.
- Если в FitBase включено «скрывать количество свободных мест», сайт должен соблюдать ту же настройку. Способ чтения настройки нужно подтвердить в P0.

## P1. Заявки сайта в воронке FitBase

### Профит

1. Администратор видит сайт, приложение и другие каналы в одной воронке.
2. Не нужно вручную переносить имя, телефон и UTM из Telegram.
3. Можно измерить цепочку `реклама → заявка → клиент → первое посещение → абонемент`.
4. Можно контролировать время до первого действия менеджера и не терять заявки между сменами.
5. После проверки базовой синхронизации можно автоматически создавать задачу ответственному сотруднику.

Количественную ценность считаем так:

- сэкономленные часы в месяц = число заявок × минуты ручного переноса / 60;
- дополнительная выручка = число заявок × доля потерянных или поздно обработанных × конверсия в покупку × средний первый чек.

До запуска зафиксировать baseline: заявки в месяц, среднее время первого контакта, долю заявок, вручную заведённых в FitBase, конверсию в первое посещение и покупку.

### Почему это не «один POST»

Основные риски — дубли по телефону, справочники источников/этапов/филиалов, повтор запроса после сетевого timeout, права токена и мониторинг персональных данных. Ненадёжный fire-and-forget после отправки формы не принимаем.

### Целевая архитектура

```text
Browser
  → lead-intake
    → YDB: заявка сохранена
      ├→ Telegram delivery queue → Telegram
      └→ FitBase delivery queue  → FitBase Lead
```

- Ответ пользователю зависит только от успешного сохранения в YDB.
- Telegram и FitBase доставляются независимо и имеют независимые статусы, retry и алерты.
- Недоступность FitBase не ломает форму и не задерживает человека.
- При успехе сохраняется ID заявки FitBase.

### Этапы реализации

#### 1. Mapping и политика дублей

Минимальный payload:

- имя;
- нормализованный телефон;
- предпочтительный способ связи;
- Telegram username, если выбран Telegram;
- UTM и click IDs;
- источник «Сайт zvenfit.ru»;
- филиал, если контекст однозначен;
- локальный `lead_id` в доступном внешнем/описательном поле.

Текущая форма не знает выбранную услугу, тренера и филиал. Если эти данные нужны в CRM, добавить безопасный контекст перехода на форму: `source_page`, `service`, `trainer`, `club`. Значения должны проверяться по allowlist на сервере, а не приниматься как произвольный CRM ID из браузера.

До кода согласовать правило:

- повторный телефон обновляет существующую открытую заявку;
- либо создаёт новую заявку как новый интерес;
- либо решение зависит от давности и этапа предыдущей заявки.

#### 2. Надёжная очередь FitBase

Добавить YDB-миграцию с отдельными полями и индексом доставки, например:

- `fitbase_status` (`pending`, `sending`, `sent`, `failed`);
- `fitbase_attempts`;
- `fitbase_due_at`;
- `fitbase_delivery_token`;
- `fitbase_lead_id`;
- `fitbase_last_error`;
- `fitbase_synced_at`.

Существующий минутный timer может обрабатывать обе очереди. Паттерн lease + delivery token + retry уже реализован для Telegram и должен быть переиспользован, а не написан заново без защиты от параллельной доставки.

#### 3. Клиент FitBase и наблюдаемость

- отдельный write-token с минимальными правами хранится только в окружении Cloud Function;
- timeout и retry с backoff;
- структурированные события без имени, телефона и тела ответа FitBase;
- метрики pending, oldest pending age, success, retry и permanent failure;
- alert на permanent failure и застрявшую очередь;
- unit-тесты клиента, mapping, дедупликации и retry;
- интеграционный тест выполняется только на согласованной тестовой заявке.

#### 4. Задача менеджеру — после MVP

Создание `Task` откладываем до стабильной синхронизации `Lead`. Для него нужно отдельно согласовать ответственного, тип задачи, SLA, филиал и поведение при повторной заявке. Если сама конфигурация FitBase умеет создавать задачу на новый API Lead, дублировать её через API не нужно.

### Предварительная оценка

После подтверждения API:

- простой небезотказный push: 1–2 человеко-дня, но в production не рекомендуем;
- надёжный MVP `Lead` с YDB retry, дедупликацией, тестами и метриками: 4–7 человеко-дней;
- автоматический `Task` и маршрутизация по филиалам/услугам: ещё 1–3 человеко-дня после MVP.

Главная неопределённость — не код очереди, а фактическая схема `Lead`, правила дублей и доступные поля вашего аккаунта FitBase.

### Критерии готовности MVP

- 100% успешно принятых сайтом заявок либо синхронизированы, либо видны в retry/failed состоянии;
- повторная обработка одной YDB-заявки не создаёт дубль в FitBase;
- временная ошибка FitBase не влияет на ответ формы;
- Telegram продолжает работать независимо;
- UTM и рекламный источник видны в FitBase;
- персональные данные и тело ответа FitBase не попадают в логи;
- есть runbook для повтора permanent failures;
- измеряются sync success rate, lag и duplicate rate.

## Порядок действий

1. Провести P0 и зафиксировать ответы по IDs, registrations, Lead и native deep links.
2. В FitBase создать/проверить рекламный источник «Сайт zvenfit.ru», этап входящей заявки и минимальный write-token.
3. Снять baseline по текущей обработке заявок.
4. Реализовать надёжный MVP `YDB → FitBase Lead`, не меняя пользовательский контракт формы.
5. Реализовать общий компонент ближайших занятий и сначала включить его на 1 странице тренера и 1 странице услуги.
6. Проверить клики по приложению и корректность выдачи; затем раскатить на остальные страницы через конфиг.
7. Добавить агрегированные места и лист ожидания после подтверждения transport contract и правил кеширования.
8. Через 2–4 недели после запуска сравнить baseline и решить, нужны ли `Task`, маршрутизация и native deep links.

## Метрики результата

### Установка приложения и расписание

- показы блока ближайших занятий;
- CTR блока в App Store / RuStore / APK;
- CTR по странице услуги и тренера;
- доля пустых/ошибочных состояний блока;
- расхождение показанных мест с FitBase в контрольной выборке.

### Заявки

- доля заявок сайта, дошедших до FitBase;
- медианный и p95 lag синхронизации;
- permanent failure rate;
- duplicate rate;
- время от заявки до первого действия менеджера;
- конверсия сайта в первое посещение и первую покупку.

## Вне текущего плана

- web-запись через виджет FitBase;
- собственная авторизация клиента на сайте;
- покупка и оплата абонемента на сайте;
- публичная выдача списка записавшихся клиентов;
- собственная реализация листа ожидания;
- замена мобильного приложения web-кабинетом.
