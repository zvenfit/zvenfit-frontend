# Риск удаления ассетов при откате Astro

Находки от 2026-10-21 для следующего разбора с Claude. Пользователь попросил
сохранить их отдельно и вернуться позже. Защита деплоя пока не реализована;
предложения ниже не внесены в основной [план миграции](astro-migration-plan.md).

Область: основной сайт ZvenFit, релизы Astro A и B. Проверенный срез
репозитория: `7c759e5e1adc2e806997c9ca31224cf2c82862b2`, редакция 4 плана.
Это риск будущего отката, установленный по коду и плану; сбой на production
этим разбором не воспроизводился.

## Полный откат возвращает удаление до замены HTML

Первая загрузка в
[`_deploy-environment.yml`](../../.github/workflows/_deploy-environment.yml)
(строки 544–552 проверенного среза) использует `aws s3 sync --delete` и
исключает только `*.html`, `robots.txt`, `sitemap.xml`. Префикс `_astro/`
не исключён. В [`package.json`](../../package.json) команда `deploy:yc`
повторяет эту схему. По [контракту AWS CLI](https://docs.aws.amazon.com/cli/latest/reference/s3/sync.html)
объекты, которых нет в источнике и которые не исключены фильтрами,
удаляются из назначения при `--delete`.

В редакции 4 плана новый порядок загрузки входил в релиз A. Поэтому полный
revert A возвращает одновременно legacy-сборку и старый workflow:

1. В бакете ещё лежит HTML A со ссылками на `/_astro/`.
2. В legacy `dist/` файлов `_astro/` нет. Первый проход удаляет их из бакета.
3. HTML A заменяется только третьим проходом. Между проходами его ссылки
   ведут на уже удалённые файлы.

[`deploy-lead-intake.test.cjs`](../../scripts/__tests__/deploy-lead-intake.test.cjs)
(строки 498–509) требует ровно три команды `sync`; полный revert возвращает
и этот контракт. §9 редакции 4 опирается на выключенный четвёртый проход,
но при таком откате исчезает сам workflow с этим проходом. Отключение
очистки только на исходной выкладке A проблему не решает.

## CDN и финальный E2E не закрывают окно

Кэш CDN может сохранить ранее запрошенные ассеты, однако наличие всех
нужных файлов в нём не гарантировано. Фактическое кэширование HTML ещё
предстоит проверить по R12. Если HTML A остаётся в CDN, ссылки на удалённые
ассеты могут сохраняться и после завершения отката, до обновления HTML.

Staging E2E выполняется после полной загрузки. Он может подтвердить уже
восстановленный legacy-сайт, пропустив недоступность ассетов между первым
и третьим проходами.

## Предложение для обсуждения с Claude

Выпустить защиту отдельным PR в `main` ещё на legacy, до ветки и релиза A.
В одном PR изменить workflow, `deploy:yc` и тесты:

- Ассеты загружаются без `--delete`; затем идут crawl-файлы, HTML и конфиги.
- Четвёртый проход очистки имеет явный переключатель, по умолчанию
  выключенный в обоих способах деплоя. Без его включения исполняются три
  прохода; очистка допускается только после успешных предыдущих проходов.
- Ветка A наследует эту базу. Обычный полный revert A сохраняет защиту;
  ручной частичный откат во время инцидента не требуется.

Дополнительное уточнение Codex: не включать очистку автоматически
«следующим релизом». Сначала определить и закрыть окно отката, проверить
срок жизни HTML в CDN и правила хранения старых ассетов. Очистка должна
оставаться выключенной при A, B и их откатах в течение этого окна.

## Что проверить при возвращении

1. Сверить актуальные SHA, workflow, `deploy:yc` и план: находки относятся
   к указанному выше срезу. Обсудить с Claude границы предварительного PR.
2. Выбрать источник переключателя и проверить, что отсутствующее значение
   запрещает очистку, а унаследованная настройка окружения не включает её
   неожиданно при rollback.
3. Проверить локально с имитацией хранилища legacy → A → полный revert A,
   останавливая выполнение после каждого прохода. Ассеты A должны оставаться
   доступны до и после замены HTML при выключенной очистке. Проверить также
   прерывание загрузки и аналогичный откат B.
4. Проверить одинаковые фильтры ассетов в первом и четвёртом проходах,
   отсутствие удаления в первом, порядок, переключатель и паритет CLI с
   workflow. Одного подсчёта команд недостаточно.
5. Перед выпуском A/B проверить дерево после полного revert: защита и её
   тесты сохраняются. Повторить сценарий с реальным артефактом релиза.
6. Проверить CDN по R12. Отдельно решить, когда разрешать удаление и какие
   версии ассетов хранить; два последних релиза сами по себе не задают
   безопасный срок для старого HTML.

После обсуждения согласованно обновить §2, §6, этап 0, A1, §9, риски и R7
основного плана. Если no-cache для конфигов также переносится на legacy,
уточнить R3 и проверить фактические заголовки уже существующих объектов:
обычный `sync` не обновляет метаданные неизменённых файлов.

На момент сохранения заметки изменена только документация. Workflow,
`deploy:yc`, тесты, облако и production не менялись; PR с исправлением
не создавался.
